# Alert Dashboard Specification

## Purpose

Interface for landlord admins to browse, filter, and acknowledge SystemAlert notifications generated by background processes (heartbeat timeout, subsystem failures).

## Requirements

### Requirement: Fix HandleInertiaRequests unread count guard

The system MUST include `Landlord` instances in the guard check so admins see their unread notification count in shared Inertia props.

#### Scenario: Admin sees unread count

- GIVEN a Landlord user with unread notifications
- WHEN `HandleInertiaRequests::share()` resolves `unread_notifications_count`
- THEN it MUST return the actual unread count (not 0)

#### Scenario: Tenant user unaffected

- GIVEN a Tenant User without unread notifications
- WHEN the guard check evaluates
- THEN the count MUST remain 0 (unchanged behavior)

### Requirement: AlertController index with filters

The system MUST return a paginated list of system alerts (`data->>'category' = 'system'`) with severity, read/unread, and date range filters via query params.

#### Scenario: Default index returns system alerts paginated

- GIVEN the landlord admin is authenticated
- WHEN they `GET /admin/alerts`
- THEN the response MUST contain paginated notifications where `data->>'category' = 'system'`
- AND the response MUST include pagination metadata (current_page, last_page, total)

#### Scenario: Filter by severity

- GIVEN notifications with mixed severity values (critical, warning, info)
- WHEN they `GET /admin/alerts?severity=critical`
- THEN the response MUST only include notifications where `data->>'severity' = 'critical'`

#### Scenario: Filter by read/unread status

- GIVEN some notifications are read (`read_at IS NOT NULL`) and some are unread
- WHEN they `GET /admin/alerts?read=false`
- THEN the response MUST only include notifications where `read_at IS NULL`

#### Scenario: Filter by date range

- GIVEN notifications created on different dates
- WHEN they `GET /admin/alerts?from=2025-01-01&to=2025-06-01`
- THEN the response MUST only include notifications where `created_at` falls within that range

#### Scenario: Empty state

- GIVEN no system notifications exist in the database
- WHEN they `GET /admin/alerts`
- THEN the response MUST return an empty paginated collection (`data: []`)

#### Scenario: Validates query params

- GIVEN an invalid severity value like `?severity=invalid`
- WHEN the request is processed
- THEN the server SHOULD return 400 or silently ignore the invalid param

### Requirement: Mark notification as read

The system MUST mark a single system notification as read via `POST /admin/alerts/{notification}/read`.

#### Scenario: Successfully marks as read

- GIVEN an unread system notification exists
- WHEN they `POST /admin/alerts/{notification}/read`
- THEN the notification's `read_at` MUST be set to the current timestamp
- AND the response SHOULD redirect back with a success flash

#### Scenario: Already-read notification is idempotent

- GIVEN a notification that is already read (`read_at IS NOT NULL`)
- WHEN they `POST /admin/alerts/{notification}/read`
- THEN the `read_at` timestamp MUST remain unchanged
- AND the response SHOULD not error

#### Scenario: Notification not found returns 404

- GIVEN a notification UUID that does not exist
- WHEN they `POST /admin/alerts/missing-uuid/read`
- THEN the response MUST be 404

#### Scenario: Non-system notification returns 404

- GIVEN a notification where `data->>'category' != 'system'`
- WHEN they `POST /admin/alerts/{notification}/read`
- THEN the response MUST be 404

### Requirement: Inertia page with filter UI

The system MUST render a `landlord/alerts.tsx` page with filters (severity dropdown, read/unread toggle, date pickers), a paginated alert list with severity badge and mark-as-read action, and an empty state.

#### Scenario: Renders alert list with data

- GIVEN the landlord admin navigates to `/admin/alerts`
- WHEN the page loads
- THEN it SHOULD display severity badges, timestamps, message preview, and a mark-as-read button for each alert

#### Scenario: Filter interaction triggers server visit

- GIVEN the user selects a filter (e.g., severity=critical)
- WHEN the filter changes
- THEN the page MUST perform an Inertia visit with the filter as query params
- AND the URL MUST update to reflect the filter state

#### Scenario: Empty state renders gracefully

- GIVEN no system alerts exist
- WHEN the page renders
- THEN it MUST show an empty state message ("No hay alertas de sistema")

### Requirement: Sidebar badge for admin alerts

The system MUST show an "Alertas" nav item with unread count badge in the admin sidebar section.

#### Scenario: Admin sees badge with count

- GIVEN the landlord admin is authenticated and has unread notifications
- WHEN the sidebar renders
- THEN it MUST display an "Alertas" link with a red badge showing the unread count

#### Scenario: Tenant does not see alerts nav

- GIVEN a tenant user (not admin) is authenticated
- WHEN the sidebar renders
- THEN it MUST NOT display the "Alertas" nav item

## Non-functional Constraints

- **Performance**: Badge count MUST use `count`, not `get` — no unnecessary hydration of notification rows
- **PostgreSQL JSON**: Filtering by `data->>'category'` MUST work on the landlord database (PostgreSQL)
- **No migrations**: All behavior MUST use the existing `notifications` table — no schema changes
- **Authorization**: All alert routes MUST be behind `auth` + `verified` + `EnsureUserIsAdmin`
